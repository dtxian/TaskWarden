## 2. 运行时结构

`[事实]` 四层单向依赖：**React 表示层 → `core/` 调度 → `runtime/` 进程 → `infra/` 基础设施**。

| 线程 | 数量 | 触发 | 关键点 |
|---|---:|---|---|
| supervisor | 1 | 250ms tick + `recv_timeout` | 唯一状态机推进者，整体包 `catch_unwind` |
| events | 1 | 阻塞 `recv` | `Event` → 前端 `notice` / `log-event` |
| snapshot | 1 | 250ms | 全量 DTO 推 `snapshot`；窗口不可见时跳过 |
| pump | 每进程 ×2 | 逐字节读管道 | 防止子进程写满管道阻塞 |
| probe | 短命 ×N | tcp/http | 结果经 `Command::ProbeDone` 回灌 |
| reaper | 短命 ×N | 停机 | graceful → `taskkill /T /F` → `TerminateJobObject` |

**零异步运行时**：只用 `std::thread` + `std::sync::mpsc`，无 tokio。

`[事实]` IPC 协议：

- 命令 15 条：`list_snapshot, start, stop, restart, start_all, stop_all, crash, reset_breaker, add_task, update_task, remove_task, set_fault_inject, shutdown, get_logs, clear_logs`；
- 事件 3 类：`snapshot`（4Hz）、`log-event`、`notice`；
- 出参 DTO `camelCase`，入参 `TaskConfig` `snake_case`；
- `backoffUntilMs` 是绝对 unix 毫秒；`LogLineDto.t_ms` 是 `f64`（历史妥协）。

## 3. 双身份：落地页 + 桌面版

`[事实]` 同一份前端代码按 `isTauri` 分流：

| 环境 | 入口 | 数据源 | 产物 |
|---|---|---|---|
| 浏览器 / GitHub Pages | `LandingApp` | `useSimulatorMock()` 本地模拟 | 产品介绍 + 可交互原型 |
| Tauri 桌面版 | `SoftwareApp` | `invoke` + `listen` | 仅软件本体窗口 |

`[事实]` 落地页不是附属品，而是项目的工程说明：`src/data/content.ts`（模块树/分层/承诺/性能/边界）+ `src/data/snippets.ts`（8 段实现代码）。

`[推断]` 这也是当前架构最大的隐性成本：**同一套交互语义维护两遍**（mock 与 live），并已出现刻意差异（`always` 下 code-0 秒退的熔断计数在 mock 中不还原）。

## 4. 构建与发布链路

`[事实]`

| 环节 | 现状 | 代价 |
|---|---|---|
| 前端构建 | Vite 6 + React 18.3.1 + Tailwind 4 | `npm ci`，Node 依赖树约 100+ 包 |
| Rust 构建 | Tauri CLI 调 `cargo`，`generate_context!` 编译期读取 `dist/` | **必须先 `npm run build`**，否则 Rust 构建失败 |
| 本机（WSL） | 无 cargo；Docker `rust:1.89-bookworm` + mingw-w64 → `x86_64-pc-windows-gnu` | 首建 ~9min，增量 ~18s |
| 产物 | `deploy/out/taskwarden.exe`（~26MB）+ **同级 `WebView2Loader.dll`** | 不是严格意义的单文件 |
| CI | `ci.yml`：frontend（ubuntu）+ backend（windows-latest） | 两个平台、两条工具链 |
| 发布 | GitHub Pages（`/TaskWarden/`）+ 便携 exe | WebView2 运行时由系统提供 |

`[事实]` 已知坑（详见 `AGENTS.md` §10）会随框架迁移消失或保留：

| 坑 | 迁移到 ZSUI 后 |
|---|---|
| DTO camelCase / snake_case 漂移 | **消失**（无 IPC 序列化） |
| `sameTask` 字段级比较、4Hz 重渲染治理 | **改变形态**（改为视图重建成本治理） |
| mock / live 双份语义 | **落地页独立后消失**；桌面端只剩真实后端 |
| `dist/` 被 gitignore 但编译必需 | **消失** |
| `capabilities/default.json` 权限 | **消失** |
| `%APPDATA%` 迁移、原子落盘、日志净化 | **保留**（`infra/` 原样复用） |
| 交叉编译 + `WebView2Loader.dll` | 需重新验证；预期改善（无 WebView2） |

## 5. 性能基线（现有宣称）

`[事实]` 仓库内已记录的性能数字（来自 `AGENTS.md` §11 的历史审计，非本次实测）：

- 监督引擎 RSS ≈ **53MB**（Tauri 进程内）；
- 窗口就绪 **45–65ms**（历史实测口径）；
- 前端 4Hz 快照 + 字段级复用，窗口隐藏时跳过 IPC。

`[推断]` 这两个数字只覆盖「应用进程」，不覆盖 WebView2 子进程树。ZSUI 官方的对照数据（见 `01`，非本机实测）显示 Tauri 全进程树可达 330–365MB；这与本项目「轻量级」的第一定位存在张力，但是否作为迁移理由，需要本次在**本机 Windows** 上重测后才能下结论（列入 `04`）。

## 6. 痛点清单（迁移动机逐条核对）

| # | 痛点 | 是否真实存在 | 迁移能否解决 |
|---|---|---|---|
| P1 | 双语言 + 双数据层，语义要维护两遍 | `[事实]` | ZSUI 单语言单进程可解；但落地页必须拆分保留 |
| P2 | 4Hz 全量 DTO + `sameTask` 手工 memo | `[事实]` | 无 IPC；但改为「视图重建成本」，需实测 |
| P3 | WebView2 进程树内存高 | `[推断]` 需本机实测 | 可解 |
| P4 | 交叉编译产出依赖 `WebView2Loader.dll` | `[事实]` | 预期可解，需验证 gnu 工具链 |
| P5 | 本机无 Rust，Rust 侧验证只能靠 CI / Docker | `[事实]` | 不解决；反而 ZSUI 无前端层，CI 更简单 |
| P6 | 自定义视觉（深色 egui 风、卡片、脉冲、sparkline） | `[事实]` | **会退化**：ZSUI 只给主题 token + Canvas 自绘 |
| P7 | 落地页在线演示是产品资产 | `[事实]` | **会失去「同源代码」叙事**，需保留独立 `web/` |
| P8 | 自定义无边框标题栏 + 拖拽 | `[事实]` | ZSUI `decorations(false)` + `custom_title_bar` 可用，但需验证 |
| P9 | 单实例 | `[事实]` | ZSUI 无内置，需自写 Win32（约 50–80 行） |
| P10 | 文档与实现强对齐的纪律 | `[事实]` | 迁移会带来一轮文档重写成本 |

## 7. 结论（供后续文档引用）

`[推断]`

1. 这次换框架的**真实收益**是：单语言/单进程、去掉 IPC 与 DTO、显著降内存、真正单文件 exe。
2. 真实成本是：UI 全部重写、视觉与动画降级、落地页拆分、alpha 依赖风险、构建链重新验证。
3. 因此这不是「换个库」，而是「换产品外壳 + 换发布形态」。必须先做时间盒 Spike，拿到本机数据再决定。
