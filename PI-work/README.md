## 2. 文件与状态规范

### 2.1 命名

| 类型 | 规则 | 示例 |
|---|---|---|
| 主题文档 | `NN-kebab 或中文短标题.md` | `01-zsui-评估.md` |
| ADR | `NNNN-短标题.md`，四位递增 | `0001-桌面UI框架选型.md` |
| 素材/数据 | `assets/` 下按来源命名 | `assets/zsui-perf-2026-10.json` |

### 2.2 文档头（必须）

```markdown
---
status: draft | review | accepted | superseded
date: 2026-10-29
updated: 2026-10-29
owner: AI / 作者
related: [01-zsui-评估.md, 02-迁移方案.md]
---
```

### 2.3 状态机

```
draft ──> review ──> accepted
  │          │
  └──────────┴────> superseded（保留，注明替代文档）
```

- `draft`：可随时改，结论未定。
- `review`：等作者审核，**禁止据此动代码**。
- `accepted`：已拍板，后续变更走新 ADR。
- `superseded`：被新文档取代，保留历史。

### 2.4 事实标记

文中每条关键结论必须可追溯：

| 标记 | 含义 |
|---|---|
| `[事实]` | 仓库/源码/官方文档可直接核对，附路径或链接 |
| `[实测]` | 本次在指定环境跑出的数字，必须写环境与命令 |
| `[推断]` | 基于事实的工程判断，允许错，必须说明依据 |
| `[待验证]` | 未验证的假设，进入 `04-验证清单.md` |

外部数据必须带**链接 + 访问日期**（ZSUI 是 alpha，数据半年就会过期）。

## 5. 协作约定

1. 先读 `00` 与 `01`，再读方案；不接受「直接给结论」。
2. 任何性能数字必须注明：机器、系统、构建方式、采样次数、是否含子进程。
3. 任何「ZSUI 支持 X」必须指到具体 feature / 源码文件 / 文档链接；指不到就写 `[待验证]`。
4. 不改代码的调研阶段，**不要**顺手重构仓库；方案通过后再开分支。
5. 迁移期间 `src-tauri/` 保持可构建，直到 `04` 全量验收通过。
