# 02 · 迁移方案（ZSUI 历史方案）

> **2026-10-29 已被 `06-Qt-迁移执行计划.md` 取代。** 最终方案是 Qt 6 + Rust 静态库（C ABI）；本文保留为 ZSUI 路线的评估与对比，不要据此执行。

> 前置：先读 `00-现状基线.md` 与 `01-zsui-评估.md`。
> 本文给出三种可选路线、推荐路线的前提条件、目标仓库结构、模块映射与阶段计划。
> **2026-10-29 作者已确认方向**：单文件小工具、无辅助子进程、体积上限 12 MiB（详见 §0）。
> **方案细节（时间预算/冻结窗口/存储位置）仍待审核，审核前不进入 P2。**

---

## 0. 已确认目标（2026-10-29）

| 项 | 决定 |
|---|---|
| 方向 | 换掉 Tauri + WebView2，走原生 Rust（ZSUI） |
| 进程模型 | **1 个应用进程**；应用自身不产生辅助进程（无 WebView2 helper、无 `conhost`、无 `taskkill`） |
| 被守护任务 | 仍由应用派生，属于产品语义，不计入「辅助进程」 |
| 体积 | **exe ≤ 12 MiB**（目标 3–5 MiB，12 MiB 为硬上限） |
| 落地页 | 保留，拆为独立 `web/`，不再与桌面端同源 |
| 视觉 | 接受原生质感 + 深色/橙色 accent + 状态色；不做 1:1 还原 |
| 依赖面 | 接受使用 ZSUI 非 stable 接口（托盘/主题/Canvas/Toast），锁版本并收敛到 facade |
| 许可证 | 接受 MPL-2.0 依赖，新增 `THIRD_PARTY_NOTICES.md` |
| 待定 | `data/` 便携目录是否保留（若要求「严格单文件」，需改 `%LOCALAPPDATA%` 或单数据文件） |

> 体积口径：exe 本体（strip + LTO 后），不含 `data/`；对照现状 ~26MB + `WebView2Loader.dll`。

## 1. 三种路线

| 路线 | 做法 | 收益 | 代价 | 适用前提 |
|---|---|---|---|---|
| **A. 不换框架** | 保留 Tauri 2 + React，只做定点优化 | 零迁移风险；保留视觉与网页 demo | WebView2 重量、双语言、DTO 双份语义仍在 | 「自定义视觉 + 在线演示」优先级最高 |
| **B. 迁移 ZSUI** | 核心 Rust 原样复用，UI 重写为原生 Rust | 单语言/单进程、内存降一个量级、真正单文件 | UI 重写 6–8 周；视觉降级；alpha 风险 |  Spike 10 项门禁全过 |
| **C. 迁移其他原生框架** | Iced / GPUI / egui / Xilem / Slint | 比 ZSUI 成熟 | 各有硬伤：Slint 许可证+体积、egui 内存/CJK、Iced 托盘/无障碍、GPUI 分发 | B 的 Spike 失败且仍要离开 Tauri |

**推荐：先做 B 的 Spike，用数据决定；不通过则回到 A，而不是仓促转 C。**
理由：A 的成本是确定的（可接受），C 只是把 alpha 风险换成另一组工程风险，且没有解决「视觉/落地页」的核心矛盾。
候选横向对比见 `05-框架候选对比.md`；若 B 失败，唯一值得进入 Plan B 的是 **Iced**。

## 2. 目标仓库结构（路线 B）

```
TaskWarden/
├─ Cargo.toml                    # workspace
├─ crates/
│  ├─ taskwarden-core/           # 纯逻辑，无 UI 依赖
│  │  ├─ src/core/               # supervisor / scheduler / breaker / health / events
│  │  ├─ src/runtime/            # process / job / killer
│  │  └─ src/infra/              # config / logbuf / sysinfo
│  ├─ taskwarden-app/            # ZSUI 应用
│  │  ├─ src/main.rs             # 窗口 + 托盘 + 单实例 + 事件循环
│  │  ├─ src/bridge.rs           # 引擎线程 ↔ UI 状态（替代 backend.rs）
│  │  ├─ src/viewmodel.rs        # SimTask 的替代：纯数据 + 格式化（可单测）
│  │  └─ src/view/               # 视图（见 §4）
│  └─ taskwarden-cli/（可选）     # 无头诊断 / 压测入口
├─ web/                          # 原落地页（React，仅 mock，独立构建）
├─ build/                        # 图标源文件
├─ deploy/                       # 交叉编译 / 服务脚本（按需重写）
├─ PI-work/                      # 本目录
└─ .github/workflows/
```

关键点：

- `crates/taskwarden-core` **不出现 zsui / tauri 依赖**，保持可单测、可跨平台编译。
- `web/` 与 `crates/` **互不依赖**：落地页不再假装「与桌面端同源」，只保留模拟原型；README 叙事同步改写。
- 旧 `src-tauri/` 在全量验收通过前保留在主分支；迁移在独立分支/worktree 进行。

## 4. 桥接设计（替代 Tauri IPC）

### 4.1 数据流

```
[supervisor 线程 250ms]
      │ Command::Snapshot / Event::Log
      ▼
[bridge 线程]  ── 写 ViewModel（不可变快照，Arc 交换）──►  Arc<ViewModel>
      │                                                        │
      │ invalidation.request_rebuild()                         │
      ▼                                                        ▼
[ZSUI UI 线程]  view(&ViewModel) 读取 Arc ────────────────► 绘制
```

### 4.2 关键约束

1. `view()` 里**不能加锁**、不能做 IO、不能等引擎。`bridge` 每 tick 生成新的 `Arc<ViewModel>` 再原子交换（`arc_swap` 或 `Mutex<Arc<T>>` 只持有一瞬）。
2. 日志不要每 tick 深拷贝全部 12×200 行。只维护：
   - 任务摘要（状态/倒计时/探针/指标）——每 tick 更新；
   - **当前选中任务**的日志 `Arc<Vec<LogLine>>` —— 仅在选择变化或该任务新增行时重建；
   - 每任务 `log_generation: u64`，视图按 generation 决定是否重建列表。
3. 命令走 `try_send`（非阻塞）。队列满时在 UI 上提示「引擎忙」，绝不阻塞 UI 线程。
4. 窗口隐藏时**停止** `request_rebuild()`（现有行为：`is_visible()` 为假跳过快照）。ZSUI 是否暴露可见性需在 Spike 中确认；若没有，用窗口状态回调 + 托盘状态自行维护。
5. 删除全部 serde DTO 派生；`serde` 只保留给 `config.toml`。

### 4.3 消息与更新

```rust
enum Msg {
    Select(TaskId), Start(TaskId), Stop(TaskId), Restart(TaskId),
    StartAll, StopAll, Crash(TaskId), ResetBreaker(TaskId),
    OpenAdd, OpenEdit(TaskId), CloseModal,
    SubmitDraft(TaskDraft), Delete(TaskId), ConfirmDelete(TaskId),
    ToggleAutoScroll, ClearLogs, SetFaultInject(bool), Quit,
}
```

`update()` 只做三件事：改 UI 局部状态、向引擎 `try_send(Command)`、必要时 `quit()`。
业务规则（熔断、DAG、进程）**一律不进入 UI 层**。

## 5. 视图实现策略（决定工作量与视觉还原度）

ZSUI 没有卡片/徽章/动画组件，先做选择，再排期：

| 方案 | 做法 | 视觉还原 | 成本 |
|---|---|---|---|
| **V1 原生语义** | `column`/`row` + `text` + `button` + 状态色 `ColorRole` | 60% | 低（推荐先做） |
| **V2 半自绘** | 卡片底/状态条用 `Canvas` 圆角矩形，文字用 `text` | 80% | 中 |
| **V3 全自绘** | 整卡/整条日志用 `Canvas`（含命中测试、滚动手势自己写） | 90%+ | 高，且丧失原生无障碍 |

`[推断]` 建议 **V1 先跑通全流程，再对「状态色条 + sparkline + 日志着色」做 V2**。不要一上来 V3，否则等于自己写一个 UI 框架。

## 6. 分阶段计划（时间盒）

> 估算是**单人有经验 Rust 开发者、全职**；按每天 4h 投入约放大 1.8–2 倍。

### P0 · 环境与骨架（2–3 天）

- 安装 Rust（本机 WSL）+ `x86_64-pc-windows-gnu` target；或在 Windows 侧装 MSVC。
- 建 workspace，`taskwarden-core` 原样搬入并跑通 `cargo test`（Linux 上 core 应可编译，`runtime`/`infra` 需 `cfg(windows)` 处理或仅在 Windows 编译）。
- ZSUI hello world：本机 Linux Direct（若 WSL 有 X11/Wayland）或 Docker 交叉到 Windows。

**出口**：`cargo build` 产出可启动窗口；`cargo test -p taskwarden-core` 通过。

### P1 · Spike（8–10 天，硬门禁）

只做验证，不追求产品完成度。10 项门禁见 `04-验证清单.md` §1。

**出口**：10 项全绿 → Go；任一红 → No-Go，回到路线 A，并把结论写入 ADR。

### P2 · 核心迁移与外壳（5–7 天）

- `core` / `runtime` / `infra` 三模块搬迁与测试恢复（24 个 Rust 测试全绿）。
- `bridge.rs`：命令通道、快照线程、`Arc` 交换、`request_rebuild`。
- 窗口外壳：自定义标题栏、状态栏指标、启动/停止全部、托盘、单实例、关闭询问。

**出口**：能用真实后端启动/停止 5 个种子任务，托盘可恢复，日志实时滚动。

### P3 · 任务区与表单（8–10 天）

- 任务卡片/列表、状态色、倒计时、依赖名、健康度。
- 日志面板：分级着色、自动滚动、清空/复制、拖拽调高（`split_panel`）。
- 表单与校验：`parseArgs`、依赖成环禁用、路径/后缀校验（非 Windows 才做）。
- 主题 token（深色 + 橙色 accent）与 4Hz 重建性能调优。

**出口**：15 条命令全部可用；10 条核心语义（`AGENTS.md` §6）逐条对齐。

### P4 · 收尾与发布（5–7 天）

- CI：Windows `cargo test --workspace` + `cargo build --release`；Linux 只跑 `taskwarden-core`。
- 交叉构建脚本重写（Docker + mingw 或 Windows runner）。
- 移除 `src-tauri/`、`dist/` 依赖、Tauri/npm 桌面依赖。
- 文档同步：README、`content.ts`、`snippets.ts`、`AGENTS.md`、`OUT_OF_SCOPE`。
- 第三方许可：`THIRD_PARTY_NOTICES.md` 记录 ZSUI（MPL-2.0）。

**出口**：`04` §2 全量验收通过；单文件 exe 在干净 Win10/11 上冒烟通过。

**合计：28–37 人日（约 6–8 周全职）。**

## 9. 仓库与分支策略

### 9.1 分支模型

```
main                    Tauri 2 可发布版本（迁移期间保持可构建，作为退路）
 └─ spike/zsui          2 周 Spike，允许脏代码，结论可能是 No-Go
     └─ feat/zsui       Go 之后的生产迁移（从 main 新建，挑拣 spike 骨架）
         └─ main         P4 全量验收后合并，删除 src-tauri/
```

- `main` 在 P4 前不接收 ZSUI 变更；紧急修复仍可在 main 发 Tauri 版本。
- `spike/zsui` 只验证门禁，不追求代码质量；失败就保留分支 + 结论，不合并。
- `feat/zsui` 从 `main` 新建，只挑拣 spike 中验证过的骨架，避免把实验代码带进生产历史。
- 合并前打 tag：`tauri-baseline-YYYY-MM-DD`（迁移前最后状态）、`zsui-p4-YYYY-MM-DD`（首个验收版本）。

### 9.2 提交顺序（准备基线）

当前工作区有未提交内容（`AGENTS.md`、`PI-work/`、`deploy/`、`package.json`、`.gitignore`），先归一化：

```bash
# 1) 部署脚本与 npm 入口
git add .gitignore package.json package-lock.json deploy
git commit -m "chore(deploy): 入库 WSL 交叉构建与本地服务脚本"

# 2) 项目知识与方案工作区
git add AGENTS.md PI-work
git commit -m "docs: 补 AGENTS 项目知识与 PI-work 方案工作区"

# 3) 打基线 tag
git tag tauri-baseline-2026-10-29

# 4) 开 Spike 分支
git switch -c spike/zsui
```

### 9.3 可选：worktree（新旧并行）

如果需要在迁移期间**同时**构建/运行 Tauri 旧版与 ZSUI 新版：

```bash
git worktree add ../TaskWarden-zsui spike/zsui
```

代价：新目录会各自产生 `target/`（ZSUI）与 `src-tauri/target/`（Tauri），磁盘占用上升；日常开发仍建议单目录切分支。

### 9.4 CI 与发布

- P4 前：`ci.yml` 保持现状（main 的 Tauri 构建 + Pages）。
- `spike/zsui`：只跑 `cargo build --target x86_64-pc-windows-gnu` + 冒烟，不阻塞 main。
- `feat/zsui`：新增 `cargo test -p taskwarden-core`（Linux 可跑）+ Windows job 编译 exe。
- P4 合并后：`ci.yml` 改为「Windows cargo test/build + 可选 web/ 构建」；`deploy.yml` 只构建 `web/`。
- 发布产物只上传 `taskwarden.exe`，**不再打包 `WebView2Loader.dll`**。
